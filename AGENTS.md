# Инструкции для работы с Sergey Content Factory

## Общие правила

- Отвечай на русском языке, обращайся к пользователю на «ты».
- Работай как senior execution partner: доводи понятную задачу до проверенного результата, самостоятельно принимай безопасные рабочие решения.
- Перед изменениями изучай существующие файлы и `git status --short`. Сохраняй чужие изменения, рабочее поведение и утверждённый дизайн.
- Используй инструменты, skills и plugins, когда они помогают выполнить конкретную задачу.
- Не удаляй данные, не перезаписывай критичные файлы, не публикуй в production и не выполняй необратимые внешние действия без явного согласия пользователя. Уже выданное разрешение в рамках задачи учитывай без повторных вопросов.
- После существенной задачи кратко сообщай, что сделано, что проверено и какие реальные ограничения остались. Не объявляй результат проверенным без фактической проверки.

## Назначение и структура

Это репозиторий публичных материалов Sergey Korneev Content Factory: карусели Instagram, видео, исходники изображений и автоматизация публикации. Статические материалы используются через Netlify; workflows также формируют ссылки на GitHub Raw.

- `slide_*.jpg` в корне — существующий набор публичных слайдов; замена может изменить контент по уже используемым URL.
- `carousel_*` — отдельные наборы, оригиналы и версии каруселей; сохраняй их имена и структуру. SVG служат редактируемыми исходниками там, где они есть.
- `assets/` — дополнительные наборы каруселей и видео в `assets/reels/`.
- `incoming/` — входные ZIP-пакеты, JSON-манифесты, части Base64 в `carousel_*.b64/` и маркеры `.ready`.
- `published/<carousel_id>/` — подготовленные слайды, `qa-report.json` и `status.json` с состоянием публикации.
- `publish.template.json` — пример манифеста для отдельного процесса публикации через `publish.json`; его подписи являются шаблонными.
- `netlify/functions/*.mts` — серверные обработчики TypeScript для загрузки и выдачи медиа.
- `.github/workflows/` — рендеринг, проверка подключения Windsor.ai и публикация в Instagram.

## Автоматизация и внешние действия

Перед push проверяй затронутые пути и актуальные условия запуска в YAML. Изменения в этом репозитории могут запускать внешние действия:

| Workflow | Триггер в текущей реализации | Действие |
| --- | --- | --- |
| `publish-carousel.yml` | Push с изменением `publish.json` | Публикация карусели через Windsor.ai и добавление комментария |
| `carousel-publisher.yml` | Push с изменением `incoming/carousel_*.zip` или `incoming/carousel_*.json` | Проверка пакета, коммит публичных слайдов, публикация карусели и запись статуса |
| `decode-carousel-package.yml` | Push с изменением `incoming/*.ready` | Сборка ZIP из Base64, проверка, коммиты материалов и блокировки, публикация карусели |
| `render-carousel-v3.yml` | Push с изменением `carousel_05_v3/*.svg` | Рендеринг JPEG и автоматический коммит/push |
| `verify-windsor.yml` | Ручной `workflow_dispatch` | GET-запрос к Windsor.ai для проверки доступности API |

- Не используй публикационные workflows как обычные тесты. Подготовка материалов сама по себе не разрешает их публикацию.
- Не сбрасывай `status.json` и блокировку `publishing` для повторного запуска без выяснения фактического результата предыдущей попытки.
- Ошибка workflow после вызова API не доказывает отсутствие публикации. В `published/carousel_007/status.json` уже зафиксирован случай успешной публикации с последующей ошибкой парсинга ответа. Перед повтором проверяй внешний результат, чтобы не создать дубликат.
- Не изменяй целевой аккаунт без запроса. Текущие workflows задают аккаунт в коде; поле `account` манифеста не гарантирует переключения адресата.
- Ключ Windsor.ai используется через GitHub secret `WINDSOR_API_KEY`; загрузчики Netlify читают `STORY_UPLOAD_TOKEN`. Не сохраняй и не выводи значения секретов. В загрузчиках есть тестовый fallback-токен: не копируй его в новые файлы и не считай производственным механизмом авторизации.

## Медиа и манифесты

- Для входных пакетов текущие workflows требуют 2–10 JPEG-слайдов размером 1080×1350, каждый не более 8 MiB. Это ограничения реализации репозитория, а не утверждение об актуальных лимитах Instagram.
- Используй последовательные имена `slide_01.jpg`, `slide_02.jpg` и далее без пропусков. Для совместимости обоих пакетных workflows размещай слайды в корне ZIP.
- Сверяй `expected_slide_count`, если поле используется, с реальным числом слайдов. Проверяй JSON, порядок файлов, целостность архива, формат и размеры изображений.
- Для новых вариантов предпочитай отдельные понятные каталоги, не заменяй утверждённые оригиналы без запроса.
- Визуально проверяй итоговые изображения: кириллицу, переносы, поля, обрезку, читаемость и согласованность дизайна. Для видео проверяй требуемые размер, длительность, воспроизведение и звук.
- Не оставляй шаблонный текст, фиктивные данные и TODO вместо запрошенного готового результата. Существующие заглушки исправляй только в рамках относящейся к ним задачи.

## Серверные функции

- Загрузчики `carousel-upload.mts` и `story-upload.mts` принимают части через POST с действиями `chunk` и `finalize`; текущий предел части — 4 MiB.
- Карусели используют Netlify Blobs store `instagram-carousel`, видео stories — `instagram-stories`.
- Сохраняй существующие маршруты `/api/*`, заголовки загрузки, ключи хранилищ, форматы ответов и HTTP-статусы, если задача не требует их изменения.
- Выдача файлов использует длительный `immutable`-кеш. Для нового содержимого предпочитай новые имена, учитывай существующие публичные ссылки.
- `carousel-static.mts` содержит `PLACEHOLDER`; не считай этот маршрут готовым источником слайдов без отдельной проверки и реализации.

## Проверка изменений

- В текущем `package.json` есть зависимость `@netlify/blobs`, но нет scripts для build, lint, typecheck или tests. В репозитории также нет настроенного тестового набора, lock-файла и `tsconfig.json`. Не заявляй о прохождении отсутствующих проверок и не запускай несуществующие npm-команды.
- Для документации проверяй содержание, ссылки на файлы и итоговый diff; установка зависимостей не нужна.
- Для JSON проверяй парсинг и обязательные поля соответствующего workflow. Для медиа выполняй техническую и визуальную проверку готовых файлов.
- Для функций проверяй затронутое поведение доступным локальным способом; отдельно отмечай, если Netlify runtime или интеграция с Blobs не проверены. Не используй production-хранилище для пробных записей без разрешения.
- Для YAML проверяй синтаксис, триггеры, условия, пути, quoting и влияние на публикацию. Учитывай, что workflows выполняются на Ubuntu с Bash, Python, Pillow, jq и curl, а локальная рабочая среда может быть Windows/PowerShell.
- Выполняй релевантные build, lint, typecheck и tests, если они появятся или будут добавлены в рамках задачи. Исправляй ошибки, вызванные своими изменениями.
- Перед завершением проверяй `git diff --check`, `git diff` и `git status --short`; новые неотслеживаемые файлы читай отдельно, поскольку обычный `git diff` их не показывает.
- Для изменений интеграций и быстро меняющихся технологий сверяйся со свежей официальной документацией. Не обновляй зависимости и не перестраивай проект без необходимости для текущей задачи.

## Контент-стратегия

Контент должен поддерживать бизнес-логику:

ЗНАНИЯ → СИСТЕМА → КОНТЕНТ → ЛИДЫ → ПРОДАЖИ → ПРИБЫЛЬ.

### Новый центр стратегии роста

Главная задача Instagram на текущем этапе — не рассказывать биографию Сергея как основной вход в воронку, а ежедневно создавать контент, ради которого незнакомый человек хочет остановиться, досмотреть/долистать, сохранить, переслать и подписаться.

Базовая воронка внимания:

ПОЛЬЗА → ИНТРИГА → БЫСТРЫЙ РЕЗУЛЬТАТ → СОХРАНЕНИЕ/РЕПОСТ → ПОДПИСКА → ДОВЕРИЕ К СЕРГЕЮ → TELEGRAM → МИНИ-ПРОДУКТ.

Пользователь должен понимать причину подписки за несколько секунд:

«Если я подпишусь, мне регулярно будут давать полезные AI-инструменты, промпты, инструкции и способы заработка, которые самому пришлось бы искать и проверять часами».

Сергей — не главная тема каждой публикации, а лицо, куратор, фильтр качества и систематизатор полезного контента.

Новый центр позиционирования:

«Максимально полезный AI-контент для людей, которые хотят упростить жизнь, научиться использовать AI и зарабатывать с его помощью».

Личная история Сергея, управленческий опыт и переход из найма сохраняются как слой доверия и дифференциации, но не должны быть основным хуком большинства публикаций.

### Формула каждой публикации

Для Reels и каруселей по умолчанию используй:

HOOK → GAP → VALUE → PAYOFF → CTA

- HOOK — остановить скролл сильной обложкой, первым кадром или формулировкой.
- GAP — создать информационный разрыв: пользователь понимает, что ответ/результат находится дальше.
- VALUE — дать реальную практическую ценность, а не общие рассуждения.
- PAYOFF — довести обещание хука до конкретного результата, вывода, списка, шаблона или решения.
- CTA — одно понятное действие: сохранить, переслать, подписаться, написать кодовое слово, перейти в Telegram.

Хук не должен быть кликбейтом без отдачи. PAYOFF обязан соответствовать обещанию первого кадра.

### Контентные приоритеты

Ориентир для тестирования, а не жёсткая месячная квота:

1. AI-польза — около 40%:
   - промпты;
   - команды;
   - готовые шаблоны;
   - подборки инструментов;
   - инструкции;
   - экономия времени;
   - практические сценарии «сделай так».

2. AI + заработок — около 30%:
   - услуги, которые можно выполнять с AI;
   - способы монетизации навыков;
   - разбор реальных рабочих задач;
   - мини-системы и понятные шаги без обещаний лёгких денег.

3. Curiosity / WOW — около 20%:
   - малоизвестные функции;
   - неожиданные результаты;
   - «до/после»;
   - ошибки использования AI;
   - эксперименты и серии, которые создают желание вернуться.

4. Личный бренд — около 10%:
   - личный опыт только там, где он усиливает полезную мысль;
   - системность, управленческий подход, отбор и проверка решений;
   - не превращать ленту в дневник перехода из найма.

### Форматы

- Reels — главный формат охвата и привлечения новой аудитории.
- Карусели — главный формат глубокой пользы, сохранений, репостов и экспертности.
- Stories не являются обязательным ежедневным форматом. Используй их точечно для прогрева, опросов, анонсов, CTA, перевода в Telegram и усиления уже опубликованного контента.
- Не создавать Stories только ради выполнения дневной нормы.

### Основные задачи Instagram-контента

1. привлечь внимание;
2. удержать пользователя;
3. дать ощутимую ценность;
4. вызвать сохранение или репост;
5. конвертировать часть аудитории в подписку;
6. после накопления доверия переводить в Telegram и мини-продукты.

Не каждая публикация должна продавать. На этапе роста приоритет:

ПРОСМОТР → СОХРАНЕНИЕ → РЕПОСТ → ПОДПИСКА.

Монетизация следует после накопления слоя внимания и доверия:

ПОДПИСКА → TELEGRAM → ДОВЕРИЕ → МИНИ-ПРОДУКТ.

### Оценка публикаций

Каждую существенную публикацию оценивай по трём уровням:

1. Кликабельность / внимание:
   - обложка;
   - хук;
   - первый кадр;
   - понятность выгоды за 1–2 секунды.

2. Удержание:
   - логика последовательности;
   - информационные разрывы;
   - понятность;
   - ритм;
   - желание дочитать или досмотреть;
   - соответствие PAYOFF обещанию HOOK.

3. Действие:
   - сохранение;
   - репост;
   - комментарий;
   - подписка;
   - переход;
   - кодовое слово;
   - другое целевое действие из задачи.

Не создавай контент только ради заполнения календаря. Каждый материал должен иметь понятную функцию роста или монетизации.

Контент-план формируй недельными циклами: публикация → сбор фактической статистики → разбор сильных/слабых паттернов → гипотезы → следующая неделя. Не фиксируй стратегию на месяц вперёд без учёта реальных данных.

## Текст и позиционирование

- Пиши естественно и без пафоса.
- Не используй обещания гарантированного заработка, быстрых денег или гарантированного результата.
- Не изображай Сергея беспомощным новичком.
- Основной образ: системный куратор и фильтр качества, который тестирует, отбирает и объясняет полезные AI-инструменты, промпты, инструкции и способы монетизации.
- Управленческий и производственный опыт Сергея используй как доказательство системности и доверия, а не как центральную тему большинства публикаций.
- В первом экране/обложке сначала показывай выгоду для аудитории. Биография Сергея не должна вытеснять пользовательскую ценность.
- Не придумывай личные результаты, доходы, кейсы, статистику или отзывы.
- Фактические цифры и достижения используй только при наличии подтверждения.
- CTA должен соответствовать конкретной воронке и задаче публикации.
- Не добавляй навязчивую продажу, если пользователь её явно не запросил.
- До появления достаточного слоя прогретой аудитории не превращай каждый материал в продажу. Сначала формируй привычку сохранять, пересылать и возвращаться за новой пользой.
- Для обложек и первых кадров предпочитай конкретные обещания ценности: число, результат, инструмент, экономия времени, шаблон, ошибка, секрет/малоизвестная функция — при условии, что содержание действительно это раскрывает.

## Skills и инструменты

- Перед выполнением специализированной повторяемой задачи проверь, существует ли релевантный Skill.
- Если Skill точно соответствует задаче, используй его инструкции как рабочий процесс.
- Не применяй все Skills подряд и не используй нерелевантный Skill ради формального соблюдения правила.
- Если локальный Skill конфликтует с прямой инструкцией пользователя, выполняй прямую инструкцию пользователя.
- Для нового повторяемого процесса, который выполняется несколько раз и имеет устойчивые правила, предложи вынести его в отдельный Skill.
- Для визуальной задачи используй подходящий визуальный инструмент, если он реально улучшает результат, а не заменяй визуальную проверку только текстовым описанием.

## Контроль публикации

Разделяй четыре состояния:

1. Черновик.
2. Готово технически.
3. Утверждено пользователем.
4. Опубликовано и проверено.

Никогда не считай «готово технически» разрешением на публикацию.

Перед внешней публикацией:
- убедись, что пользователь дал разрешение именно на публикацию;
- проверь файлы;
- проверь порядок;
- проверь целевой аккаунт и канал;
- учитывай возможные автоматические GitHub Actions.

После публикации:
- получи доступное подтверждение результата;
- проверь порядок и отображение;
- при наличии идентификатора публикации сохрани его;
- не публикуй повторно только потому, что API или workflow вернул неоднозначную ошибку.

## Git и защита рабочего результата

- По умолчанию изменения делай локально.
- Не выполняй push, merge, release, deploy или запуск публикационного workflow без явного разрешения пользователя, если это внешнее действие.
- Перед потенциально опасным push выясни, какие workflows он запустит.
- Для нового варианта материала предпочитай новую версию или отдельную папку вместо перезаписи утверждённого результата.
- Не удаляй предыдущую рабочую версию до проверки новой.
- После изменений покажи git status и краткий diff.

## Критерий завершения задачи

Не завершай задачу словами «готово» только потому, что файл создан.

Задача считается завершённой, когда:
1. запрошенный результат создан;
2. выполнены доступные технические проверки;
3. выполнена визуальная/содержательная проверка, если она применима;
4. не осталось известных ошибок, вызванных изменениями;
5. внешнее действие выполнено только при наличии разрешения;
6. пользователю кратко сообщено, что именно сделано и что проверено.
